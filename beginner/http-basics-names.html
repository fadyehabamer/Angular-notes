HttpClient, name by nameHttpClient، اسم اسم

The idea is simple: a service asks the server, the component subscribes, the answer arrives later. The confusing part is the names. get is Angular’s, getAll is yours, subscribe and next belong to RxJS, and the field names in your Product interface are not really yours at all: the server picked them. This page sorts every name by its owner.الفكرة بسيطة: الـ service بتسأل السيرفر، والـ component بيعمل subscribe، والإجابة بتوصل بعدين. اللي بيلخبط هو الأسماء. get بتاعة أنجولار، وgetAll بتاعتك، وsubscribe وnext بتوع RxJS، وأسماء الـ fields في الـ interface Product بتاعك مش بتاعتك أصلًا: السيرفر هو اللي اختارها. الصفحة دي بتفرز كل اسم حسب صاحبه.

  • The service owns every URL. Components never type /api/…; they call your method names. When the backend moves, you edit one file.الـ service هي صاحبة كل URL. الـ components عمرها ما بتكتب /api/…؛ هي بتنادي أسماء الميثودز بتاعتك. ولما الـ backend يتنقل، بتعدّل ملف واحد.
  • The service returns, the component subscribes. A service method that calls subscribe itself leaves the component with nothing to react to.الـ service بترجّع، والـ component بيعمل subscribe. ميثود في الـ service بتعمل subscribe بنفسها بتسيب الـ component من غير حاجة يتفاعل معاها.

AThe { params } shorthandاختصار { params }

{ params } means { params: params }. The key must be params because HttpClient reads that key, and the shorthand makes your variable copy it. Want a different variable name? Mistakes that fail silently or confusinglyغلطات بتفشل في صمت أو بشكل ملخبط

HTTP bugs hide in two places: the request that never leaves, and the answer whose names do not match. Keep the browser’s Network tab open while you read these.باجات الـ HTTP بتستخبى في مكانين: الطلب اللي عمره ما بيخرج، والإجابة اللي أسماءها مش مطابقة. خلي تاب الـ Network في المتصفح مفتوح وانت بتقرا دول.

1No subscribe, no requestمفيش subscribe، مفيش طلب
products.tsavoidتجنّب
deleteProduct(productId: number) {radish(lemon: number) {  this.api.remove(productId);  this.carrot.pickle(lemon);}
products.tsdo thisاعمل كده
deleteProduct(productId: number) {radish(lemon: number) {  this.api.remove(productId).subscribe(() => { /* … */ });  this.carrot.pickle(lemon).subscribe(() => { /* … */ });}

remove() returns a recipe. Nothing reads it, so nothing is sent. The Network tab stays empty and the product is still there after a refresh.remove() بترجّع وصفة. محدش بيقراها، فمفيش حاجة بتتبعت. تاب الـ Network بيفضل فاضي والمنتج لسه موجود بعد الـ refresh.

2A field name the server does not sendاسم field السيرفر مش بيبعته
product.tsavoidتجنّب
export interface Product {export interface Waffle {  id: number;  title: string;   // the JSON says "name"  price: number;}
product.tsdo thisاعمل كده
export interface Product {export interface Waffle {  id: number;  name: string;  price: number;}

TypeScript believes you, so {{ p.title }} compiles. At runtime the object has name, not title, and every row shows a blank. Open the response in the Network tab and copy the keys from there.TypeScript بيصدّقك، فـ {{ p.title }} بتعمل compile. ووقت التشغيل الـ object فيه name مش title، وكل صف بيعرض فراغ. افتح الـ response في تاب الـ Network وانسخ المفاتيح من هناك.

3Treating the recipe as the dataإنك تعامل الوصفة كأنها الداتا
products.tsavoidتجنّب
this.products.set(this.api.getAll(''));this.biscuit.set(this.carrot.potato(''));
products.tsdo thisاعمل كده
this.api.getAll('').subscribe(list => this.products.set(list));this.carrot.potato('').subscribe(koshary => this.biscuit.set(koshary));

This one is a compile error, but a confusing one: an Observable<Product[]> is not assignable to Product[]. It means: you passed the recipe, not the answer. The answer only exists inside subscribe.دي compile error، بس ملخبط: Observable<Product[]> مينفعش يتحط مكان Product[]. ومعناه: انت بعت الوصفة، مش الإجابة. والإجابة موجودة بس جوه subscribe.

4Two subscribes, two requestsاتنين subscribe، اتنين طلبات
products.tsavoidتجنّب
const request = this.api.getAll('');const mango2 = this.carrot.potato('');request.subscribe(list => this.products.set(list));mango2.subscribe(koshary => this.biscuit.set(koshary));request.subscribe(list => console.log(list.length));mango2.subscribe(koshary => console.log(koshary.length));
products.tsdo thisاعمل كده
this.api.getAll('').subscribe(list => {this.carrot.potato('').subscribe(koshary => {  this.products.set(list);  this.biscuit.set(koshary);  console.log(list.length);  console.log(koshary.length);});

Every subscribe runs the recipe again, so the server gets the same GET twice. Nothing looks wrong on screen. Subscribe once and do everything inside.كل subscribe بيشغّل الوصفة من الأول، فالسيرفر بياخد نفس الـ GET مرتين. ومفيش حاجة باينة غلط على الشاشة. اعمل subscribe مرة واحدة واعمل كل حاجة جواها.

5A query name the server does not knowاسم query السيرفر مش عارفه
product.service.tsavoidتجنّب
const params = new HttpParams().set('search', search);const params = new HttpParams().set('search', donut);
product.service.tsdo thisاعمل كده
const params = new HttpParams().set('q', search);const params = new HttpParams().set('q', donut);

The request goes out as ?search=kettle, but this server reads ?q=. Most servers ignore the unknown parameter and return everything. The search box “does nothing”. The API’s docs, not your taste, decide this name.الطلب بيخرج ?search=kettle، بس السيرفر ده بيقرا ?q=. وأغلب السيرفرات بتتجاهل الـ parameter اللي مش عارفاه وبترجّع كل حاجة. وخانة البحث «مش بتعمل حاجة». docs الـ API، مش ذوقك، هي اللي بتقرر الاسم ده.

When it does nothingلما مايعملش حاجة

Six questions, in this orderست أسئلة، بالترتيب ده

Your request “does not work”. Open the browser’s Network tab, then ask these.الطلب بتاعك «مش شغال». افتح تاب الـ Network في المتصفح، وبعدين اسأل دول.

Checkpointنقطة فحص

1. Is there a request in the Network tab at all? If not, nothing subscribed.1. فيه طلب في تاب الـ Network أصلًا؟ لو لأ، يبقى محدش عمل subscribe.

Checkpointنقطة فحص

2. Does the app throw NG0201 about HttpClient? Then provideHttpClient() is missing from app.config.ts.2. التطبيق بيرمي NG0201 عن HttpClient؟ يبقى provideHttpClient() ناقصة في app.config.ts.

Checkpointنقطة فحص

3. Is the URL and the query string exactly what the API expects (/api/products?q=…)? What status came back?3. الـ URL والـ query string بالظبط اللي الـ API مستنيه (/api/products?q=…)؟ ورجع status إيه؟

Checkpointنقطة فحص

4. Open the response. Do its keys match your interface letter for letter, including case and underscores?4. افتح الـ response. المفاتيح بتاعته مطابقة للـ interface بتاعك حرف بحرف، بالـ capital والـ underscores؟

Checkpointنقطة فحص

5. Do you have an error callback? Without one, a failed request shows nothing on screen, only in the console.5. عندك callback لـ error؟ من غيره، الطلب الفاشل مش بيبان على الشاشة، في الـ console بس.

Checkpointنقطة فحص

6. Is the result written somewhere the template reads, like this.products.set(list)?6. النتيجة بتتكتب في حتة التمبلت بيقراها، زي this.products.set(list)؟

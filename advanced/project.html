Step 02الخطوة 02

OnPush everywhereOnPush في كل حتة

One line per component, and it is safe because you built on signals from the start — inputs are signals, state is signals, so every component already knows when its inputs change.سطر واحد لكل component، وهو آمن لأنك بنيته على signals من الأول — الـ inputs هي signals والحالة هي signals، فكل component عارفة أصلاً إمتى inputs بتاعتها بتتغير.

one line per componentrepeat 5×كررها 5 مرات
@Component({  selector: 'product-list',  changeDetection: ChangeDetectionStrategy.OnPush,  // …})
Why this never breaks your appليه دي عمرك ما هتبوّظ تطبيقك

The classic OnPush bugs come from mutating fields the template reads — push(), splice(), property writes. Your store replaced the reference on every update, exactly as the beginner project drilled. If something does stop updating after this step, that is not an OnPush bug to work around; it is a mutation bug you just discovered. Fix the mutation, not the symptom.باجات الـ OnPush الكلاسيكية بتيجي من تعديل حقول التمبلت بيقراها — push() وsplice() وتعديل خصائص. المخزن بتاعك كان ببدّل الـ reference مع كل تحديث، بالظبط زي ما مشروع المبتدئ درّبك. لو حاجة بقت مش بتتحدث بعد الخطوة دي، دي مش باج OnPush تعالجه — دي باج mutation لسه بتكتشفها. صلّح الـ mutation، مش العرَض.

Checkpointنقطة فحص

Everything still works, and the DevTools Profiler now shows far fewer components checked per interaction. Number into PERF.md.كل حاجة شغالة، والـ Profiler في DevTools دلوقتي بيعرض أقل بكتير من الـ components بتتفحص في كل تفاعل. الرقم في PERF.md.

Step 03الخطوة 03

Go zonelessدخل عالم zoneless

Delete the thing that guessed for you. Zoneless is stable in Angular v20+, and your signal-based app is already the shape it requires.شيل الحاجة اللي كانت بتخمّن بدالك. الـ zoneless مستقر في أنجولار v20+، وتطبيقك المعتمد على signals أصلاً هو الشكل اللي بطلبه.

src/app/app.config.tsswap the providerبدّل الـ provider
import { provideZonelessChangeDetection } from '@angular/core'; export const appConfig: ApplicationConfig = {  providers: [    provideZonelessChangeDetection(),    provideRouter(routes, withComponentInputBinding()),    provideHttpClient(withInterceptors([apiInterceptor])),  ],};
angular.json (polyfills)remove zone.jsشيل zone.js
"polyfills": [  // "zone.js"   ← delete this line]
the pattern that breaks zonelessavoidتجنّب
// a callback from outside Angular:chartLib.onUpdate(v => {  this.price = v;        // plain field — nobody notices});
the pattern that cannot breakdo thisاعمل كده
chartLib.onUpdate(v => {  this.price.set(v);     // signal — update is scheduled});
Measure, then compareقِس، وبعدين قارن

Re-run the idle profile. Under zone.js, every macrotask — timers, XHR, third-party callbacks — triggered a full tree walk. Zoneless with signals does targeted updates, and the idle number should drop to roughly zero. The app works identically; the machinery underneath got honest.أعد قياس الـ profile وهو واقف. تحت zone.js، كل macrotask — تايمرات وXHR وcallbacks من مكتبات — كان بيخلي لفة كاملة على الشجرة. الـ zoneless مع الـ signals بيعمل تحديثات موجهة، والرقم الموقوف المفروض ينزل لحوالي الصفر. التطبيق شغال بنفس الشكل؛ والماكينة اللي تحته بقت بتقول الحقيقة.

Checkpointنقطة فحص

Full manual pass — list, categories, detail, cart, checkout, the fake order — behaves exactly as before. Idle change-detection time into PERF.md, next to the baseline.لفة يدوية كاملة — ليستة وفئات وتفاصيل وكارت ودفع والأوردر المزوّر — شغالة بنفس الشكل بالظبط. وقت الـ change detection وهو واقف في PERF.md، جانب الخط الأساسي.

Step 04الخطوة 04

@defer the heavy parts@defer للحاجات التقيلة

The product list does not need every card's weight in the first paint. @defer ships the below-the-fold parts when they approach the viewport — declaratively, no IntersectionObserver code.ليستة المنتجات مش محتاجة وزن كل الكروت في أول رسمة. الـ @defer بيشحن الأجزاء اللي تحت لما تقرب من الشاشة — تعريفي، ومن غير كود IntersectionObserver.

product-list.html (extracted)defer on scrolldefer مع السكرول
@defer (on viewport) {  <ul class="grid">    @for (p of load().data; track p.id) {      <li>…</li>    }  </ul>} @placeholder (minimum 200px) {  <p>Product list is loading…</p>}
Best practice — a real placeholder, alwaysعادة صح — placeholder حقيقي، دايماً

@placeholder is not decoration: it reserves layout space so the deferred chunk loading does not shift the page (CLS), and it is what users on slow networks actually see. Give it real height.@placeholder مش زينة: بيحجز مساحة في التخطيط عشان تحميل الـ chunk ما يزحلقش الصفحة (CLS)، وهو اللي المستخدم على شبكات بطيئة بيشوفه فعلاً. اديله ارتفاع حقيقي.

Checkpointنقطة فحص

Network tab, throttled to Slow 4G: the main chunk loads first, and a separate chunk-*.js arrives only as the list scrolls into view. Lighthouse FCP/TBT into PERF.md.تاب Network، مضبوط على Slow 4G: الـ chunk الرئيسي بينزل الأول، وchunk-*.js منفصل بينزل بس لما الليستة تدخل الشاشة. أرقام FCP وTBT من Lighthouse في PERF.md.

Step 05الخطوة 05

Budgets: make regressions impossibleBudgets: امنع الرجوع للور

You have good numbers now. Budgets are how you keep them: the build itself fails when a bundle grows past the line you set.عندك أرقام كويسة دلوقتي. الـ budgets هي الطريقة اللي هتحافظ بيها عليهم: البيلد نفسه بيفشل لما الباندل يكبر عن الخط اللي حددته.

angular.jsonyour lines in the sandخطوطك اللي محددها
"budgets": [  {    "type": "initial",    "maximumWarning": "450kB",    "maximumError": "550kB"  },  {    "type": "anyComponentStyle",    "maximumWarning": "4kB",    "maximumError": "8kB"  }]
  • Set the warning about 10% above today's number, and the error another 10% up — tight enough to catch slop, loose enough not to nag every week.حدد التحذير حوالي 10% فوق رقم النهاردة، والخطأ 10% كمان — قريب كفاية إنه يمسك أي تضخيم، ومتسع كفاية إنه مايزنّقش كل أسبوع.
  • Prove it works: temporarily drop maximumError below your current size and watch ng build fail. Then restore. You now have a build that refuses to get fat.اثبت إنه شغال: نزّل maximumError مؤقتاً تحت حجمك الحالي وشوف ng build بيفشل. وبعدين رجّعه. دلوقتي عندك بيلد بيرفض يتسمّن.
  • This is the deployment gap in the roadmap's "not covered" list, met head-on — budget enforcement is a CI concern too, and step 08 wires it there.دي المرة الأولى اللي بنقفل فيها من فجوة "النشر والـ CI" اللي خطة التعلّم سجلتها — فرض الـ budgets موضوع CI كمان، والخطوة 08 هتوصله هناك.
Checkpointنقطة فحص

A deliberately-over-budget build fails with a clear error, a normal build passes. Initial bundle number into PERF.md beside the baseline.بيلد متضخم بقصد بيفشل بخطأ واضح، والبيلد العادي بيعدي. رقم الباندل الأولي في PERF.md جانب الخط الأساسي.

Step 06الخطوة 06

Unit tests for the cart serviceتستات وحدية لخدمة الكارت

The cart is pure logic — which means every rule you wrote can be proven in milliseconds. This is where the readonly/computed discipline pays interest.الكارت منطق نقي — يعني كل قاعدة كتبتها ممكن تتثبت في أجزاء من الثانية. هنا عادة الـ readonly والـ computed بتدّي عوايدها.

src/app/cart.service.spec.tsnew fileملف جديد
import { TestBed } from '@angular/core/testing';import { CartService } from './cart.service';import { ApiProduct } from './api/product'; const p = (id: number, price: number): ApiProduct => ({  id, price,  title: 'x', category: 'c', description: 'd', image: 'i',}); describe('CartService', () => {  let cart: CartService;   beforeEach(() => {    TestBed.configureTestingModule({});    cart = TestBed.inject(CartService);  });   it('merges the same product into one line', () => {    cart.add(p(1, 40));    cart.add(p(1, 40));    expect(cart.all().length).toBe(1);    expect(cart.all()[0].qty).toBe(2);  });   it('totals from qty × price, reactively', () => {    cart.add(p(1, 40));    cart.add(p(2, 25));    expect(cart.total()).toBe(65);    cart.setQty(2, 3);    expect(cart.total()).toBe(115);   // computed re-ran, no hand sync  });   it('removes cleanly', () => {    cart.add(p(1, 40));    cart.remove(1);    expect(cart.count()).toBe(0);  });});
Test the contract, not the implementationاختبر العقد، مش التنفيذ

Notice what is asserted: merge behaviour, reactive totals, clean removal — the contract a store page depends on. No test peeks at private fields. When you refactor the service next month, these tests stay green and that is the whole point.خد بالك من اللي بتتأكد منه: سلوك الدمج، والإجماليات المتفاعلة، والمسح النضيف — العقد اللي صفحات المتجر معتمدة عليه. ولا تست بيدخل في الحقول الخاصة. لما تعمل refactor للـ service الشهر الجاي، التستات دي هتفضل خضرا، وده كل المقصود.

Checkpointنقطة فحص

ng test passes, including the third test that would have failed before computed() existed. Test count into PERF.md.ng test ناجح، بما فيه التست التالت اللي كان هيقع قبل ما computed() تظهر. عدد التستات في PERF.md.

A Playwright smoke testتست دخان بـ Playwright

One test, the user's whole journey: see a product, add it, guard-checkout it. Topic 44 in miniature — and the test that would have caught your worst bug.تست واحد، لرحلة المستخدم كلها: شوف منتج، ضيفه، وجرّب الدفع والـ guard. الموضوع 44 مصغّر — والتست اللي كان هي مسك وحش باجاتك.

import { test, expect } from '@playwright/test'; test('a shopper can add to cart and checkout', async ({ page }) => {  await page.goto('/');  await expect(page.getByRole('heading', { name: /products/i })).toBeVisible();   // first product: open it and add  await page.getByRole('link').nth(1).click();  await page.getByRole('button', { name: /add to cart/i }).click();   // cart shows one line  await page.getByRole('link', { name: /cart/i }).click();  await expect(page.getByText(/total/i)).toBeVisible();   // checkout is now allowed by the guard  await page.goto('/checkout');  await expect(page.getByRole('heading', { name: /checkout/i })).toBeVisible();}); test('an empty cart is turned away from checkout', async ({ page }) => {  await page.goto('/checkout');  await expect(page).toHaveURL(/\/cart/);});
terminalrun against the prod buildشغّله على بيلد الإنتاج

Best practice — test roles, not CSSعادة صح — اختبر الأدوار، مش الـ CSS

getByRole, never .css-1x2y. Role queries survive restyling, they fail when accessibility breaks — which is exactly what you want a test to catch. A passing role-based smoke test is also an a11y statement.getByRole، عمرك ما .css-1x2y. الاستعلامات بالأدوار بتنجو من تغيير الشكل، وبتفشل لما الإتاحة تتكسر — وده بالظبط اللي عايز التست يمسكه. تست دخان ناجح بالأدوار هو كمان إعلان إتاحة.

Checkpointنقطة فحص

Both tests pass headless. The second one is your step-07 guard from phase 02, now permanently proven.التستين ناجحين من غير واجهة. التست التاني هو الـ guard بتاعك من المرحلة 02، دلوقتي متثبت للأبد.

Step 08الخطوة 08

Deploy, then let CI protect itانشر، وبعدين خلي الـ CI يحميه

Two moves: a real host, and a pipeline that re-proves the build, the budgets and the tests on every push. This closes the roadmap's deployment/CI gap for your own projects.حركتين: هوست حقيقي، وخط أنابيب بيعيد إثبات البيلد والـ budgets والتستات مع كل push. بدها بتقفل فجوة النشر والـ CI بتاعة خطة التعلّم في مشاريعك إنت.

Why this one yaml is a career moveليه الملف ده تحفة كاريير

E2E tests, name by nameتستات الـ E2E، اسم اسم

The idea of an end-to-end test is simple: open the real app in a real browser and use it the way a person would. The confusing part is the names. The test cannot see your classes or variables, so it connects to the app through button labels, form labels, a test id, and URL paths, all written as strings. Meanwhile words like page, button and heading look like yours but are fixed. This page sorts them out.فكرة الـ end-to-end test بسيطة: افتح التطبيق الحقيقي في متصفح حقيقي واستخدمه زي أي إنسان. اللي بيلخبط هو الأسماء. التست مش شايف الكلاسات ولا المتغيرات بتاعتك، فهو بيتوصل بالتطبيق عن طريق كلام الزراير، واللابلز بتاعة الفورم، وtest id، ومسارات الـ URL، وكلهم مكتوبين كـ strings. وفي نفس الوقت كلمات زي page وbutton وheading شكلها بتاعتك وهي ثابتة. الصفحة دي بترتّبهم.

The whole thing in one lineالحكاية كلها في سطر

An E2E test shares no TypeScript names with your Angular code. It shares what a user can see or type: labels, button text, a test id, URL paths, and the JSON shape of the API. Every one of those is a string.تست الـ E2E مش متشارك في ولا اسم TypeScript مع كود الأنجولار بتاعك. هو متشارك في اللي اليوزر يقدر يشوفه أو يكتبه: اللابلز، وكلام الزراير، وtest id، ومسارات الـ URL، وشكل الـ JSON بتاع الـ API. وكل واحد فيهم string.

App or test?التطبيق ولا التست؟

Who writes what, and who picks the nameمين بيكتب إيه، ومين بيختار الاسم

Every name on this page — yours or Angular’s?كل اسم في الصفحة دي — بتاعك ولا بتاع أنجولار؟

Read the orange rows first. Almost all of them are strings: text the user sees, a data-testid, a URL. TypeScript never checks them against the app, and Playwright does not type-check your tests at all, so every one of them fails at run time, usually as a timeout.اقرا الصفوف البرتقاني الأول. تقريبًا كلهم strings: كلام اليوزر بيشوفه، وdata-testid، وURL. TypeScript عمره ما بيشيّك عليهم قدام التطبيق، وPlaywright أصلًا مابيعملش type-check للتستات بتاعتك، فكل واحد فيهم بيفشل وقت التشغيل، وغالبًا كـ timeout.

Four places where the name is not freeأربع أماكن الاسم فيهم مش براحتك

Some of these look like ordinary JavaScript choices. They are not: Playwright reads them by exact spelling.شوية من دول شكلهم اختيارات JavaScript عادية. بس لأ: Playwright بيقراهم بالكتابة بالظبط.

AThe fixture name inside ({ })اسم الـ fixture جوه ({ })
checkout.spec.tsavoidتجنّب
test('a visitor can pay for their cart', async ({ tab }) => {
checkout.spec.tsdo thisاعمل كده
test('a visitor can pay for their cart', async ({ page }) => {

In normal JavaScript a destructured name is up to you. Here Playwright looks at the names you destructure and provides the fixture with that name. There is no fixture called tab, so the run stops with an error about it. Inside a page object you receive the tab as an ordinary parameter, and there the name is yours.في JavaScript العادي الاسم اللي بتفكّه من الأوبجكت براحتك. هنا Playwright بيبص على الأسماء اللي انت بتفكّها وبيدّيك الـ fixture اللي بالاسم ده. مفيش fixture اسمها tab، فالتشغيل بيقف بـ error عنها. وجوه الـ page object بتستلم التاب كـ parameter عادي، وهناك الاسم بتاعك.

BWhere the spec file lives, and its suffixملف الـ spec فين، وبيخلص بإيه

Playwright runs files inside testDir whose names end in .spec.ts or .test.ts by default. A file called checkout.e2e.ts, or one outside ./e2e, is simply not run.Playwright افتراضيًا بيشغّل الملفات اللي جوه testDir واللي أسماءها بتخلص بـ .spec.ts أو .test.ts. ملف اسمه checkout.e2e.ts، أو ملف برّه ./e2e، ببساطة مش هيشتغل.

CThe data-testid attributeالـ attribute اللي اسمه data-testid

getByTestId reads data-testid by default. Write data-test="cart-total" or data-qa in the template and it finds nothing, unless you change testIdAttribute in the config. The value after it, cart-total, is yours.getByTestId بيقرا data-testid افتراضيًا. لو كتبت data-test="cart-total" أو data-qa في التمبلت مش هيلاقي حاجة، إلا لو غيّرت testIdAttribute في الإعدادات. والقيمة اللي بعده، cart-total، بتاعتك.

DRole names, and how name matchesأسماء الـ roles، وname بيطابق إزاي

Role names come from the ARIA list: button, heading, textbox, link… you cannot invent one. And name matches part of the accessible name, ignoring case, unless you add exact: true. So 'Pay' would also match “Pay with PayPal”.أسماء الـ roles جاية من ليستة ARIA: button وheading وtextbox وlink… مينفعش تألف واحد. وname بيطابق جزء من الاسم، ومش فارق معاه الحروف الكبيرة والصغيرة، إلا لو ضفت exact: true. فـ'Pay' هتطابق كمان «Pay with PayPal».

Older codeكود أقدم

Protractor used the same shared namesProtractor كان بيستخدم نفس الأسماء المتشاركة

Older Angular projects came with Protractor. It is deprecated and the CLI no longer sets it up, but you will still read it. Every tool word changes; the words shared with the app do not.مشاريع أنجولار القديمة كانت جاية بـ Protractor. هو دلوقتي deprecated والـ CLI مبقاش بيجهّزه، بس لسه هتقراه. كل كلمة بتاعة الأداة بتتغير؛ لكن الكلمات المتشاركة مع التطبيق لأ.

checkout.spec.ts — Protractoravoidتجنّب
import { browser, by, element } from 'protractor'; await browser.get('/checkout');await browser.get('/noodle');await element(by.buttonText('Pay now')).click();await element(by.buttonText('Banana')).click();expect(await element(by.css('h1')).getText()).toEqual('Thank you');expect(await element(by.css('h1')).getText()).toEqual('Pickle');
checkout.spec.ts — Playwrightdo thisاعمل كده
import { expect } from '@playwright/test'; await page.goto('/checkout');await page.goto('/noodle');await page.getByRole('button', { name: 'Pay now' }).click();await page.getByRole('button', { name: 'Banana' }).click();await expect(page.getByRole('heading', { name: 'Thank you' })).toBeVisible();await expect(page.getByRole('heading', { name: 'Pickle' })).toBeVisible();

checkout, Pay now and Thank you are in both versions because they belong to the app. Also notice the old assertion reads the text once, while toBeVisible keeps retrying.checkout وPay now وThank you موجودين في النسختين لإنهم بتوع التطبيق. وخد بالك كمان إن الـ assertion القديم بيقرا النص مرة واحدة، لكن toBeVisible بتفضل تعيد المحاولة.

Mistakes that fail silently or confusinglyغلطات بتفشل في صمت أو بشكل ملخبط

An E2E failure usually says “timeout”, which tells you when it gave up, not why. Most of the time the why is a shared string that went stale.فشل الـ E2E غالبًا بيقول «timeout»، ودي بتقولك استسلم إمتى، مش ليه. وأغلب الوقت الـ «ليه» ده string متشارك بقى قديم.

1The button text changed in the appكلام الزرار اتغير في التطبيق
checkout-page.tsavoidتجنّب
// checkout.html now says: <button …>Place order</button>await this.page.getByRole('button', { name: 'Pay now' }).click();await this.melon.getByRole('button', { name: 'Banana' }).click();
checkout-page.tsdo thisاعمل كده
// checkout.html now says: <button …>Place order</button>await this.page.getByRole('button', { name: 'Place order' }).click();await this.melon.getByRole('button', { name: 'Place order' }).click();

The click waits for a button that no longer exists until the test times out. The error names the locator it was waiting for; compare that text with the screen.الكليك بتستنى زرار مبقاش موجود لحد ما وقت التست يخلص. والإيرور بيذكر الـ locator اللي كان مستنيه؛ قارن الكلام ده بالشاشة.

2A route pattern that matches nothingpattern للشبكة مش بيطابق حاجة
checkout.spec.tsavoidتجنّب
await page.route('**/api/carts', route => route.fulfill({ json: { items: [] } }));await page.route('**/api/carts', cookie => cookie.fulfill({ json: { turnip: [] } }));
checkout.spec.tsdo thisاعمل كده
await page.route('**/api/cart', route => route.fulfill({ json: { items: [] } }));await page.route('**/api/basket', cookie => cookie.fulfill({ json: { turnip: [] } }));

No error at all. The handler is registered, nothing ever matches it, and the app talks to the real backend. The test now depends on whatever data is there today.مفيش أي error. الـ handler اتسجّل، ومفيش حاجة بتطابقه، والتطبيق بيكلّم الباك إند الحقيقي. والتست بقى معتمد على أي داتا موجودة النهاردة.

3A page-object method renamed on one sideميثود في الـ page object اتغيرت من ناحية واحدة
checkout.spec.tsavoidتجنّب
await checkoutPage.pay('mona@shop.eg', '4242424242424242');await olive.pay('mona@shop.eg', '4242424242424242');
checkout.spec.tsdo thisاعمل كده
await checkoutPage.payWith('mona@shop.eg', '4242424242424242');await olive.carrot('mona@shop.eg', '4242424242424242');

Your editor underlines it, but Playwright does not type-check before running, so the run still starts and fails with “checkoutPage.pay is not a function”. If you want compile errors, run the TypeScript compiler over the test folder in CI.الإديتور بيحط تحتها خط، بس Playwright مابيعملش type-check قبل التشغيل، فالتشغيل بيبدأ عادي ويفشل بـ «checkoutPage.pay is not a function». لو عايز compile errors، شغّل الـ TypeScript compiler على فولدر التستات في الـ CI.

4Sleeping instead of waiting for stateتنام بدل ما تستنى الحالة
checkout.spec.tsavoidتجنّب
await page.waitForTimeout(2000);expect(await page.getByRole('heading').textContent()).toBe('Thank you');expect(await page.getByRole('heading').textContent()).toBe('Pickle');
checkout.spec.tsdo thisاعمل كده
await expect(page.getByRole('heading', { name: 'Thank you' })).toBeVisible();await expect(page.getByRole('heading', { name: 'Pickle' })).toBeVisible();

Two seconds is too long on your laptop and too short on a busy CI machine, and textContent() reads once with no retry. The good version retries until the heading appears.تانيتين كتير على اللابتوب بتاعك وقليل على جهاز CI مشغول، وtextContent() بتقرا مرة واحدة من غير ما تعيد. النسخة الكويسة بتعيد لحد ما العنوان يظهر.

5A name that matches two buttonsاسم بيطابق زرارين
checkout-page.tsavoidتجنّب
await this.page.getByRole('button', { name: 'Pay' }).click();await this.melon.getByRole('button', { name: 'Pay' }).click();
checkout-page.tsdo thisاعمل كده
await this.page.getByRole('button', { name: 'Pay now', exact: true }).click();await this.melon.getByRole('button', { name: 'Banana', exact: true }).click();

If the page also has “Pay with PayPal”, 'Pay' matches both, because name matches part of the text. Playwright refuses to guess and fails with a “strict mode violation”.لو الصفحة فيها كمان «Pay with PayPal»، 'Pay' هتطابق الاتنين، لإن name بيطابق جزء من الكلام. Playwright بيرفض يخمّن وبيفشل بـ «strict mode violation».

When it failsلما يفشل

Six questions, in this orderست أسئلة، بالترتيب ده

Your E2E test is red, or green when it should not be. Ask these before changing anything.تست الـ E2E بتاعك أحمر، أو أخضر وهو مايصحش يبقى كده. اسأل دول قبل ما تغيّر أي حاجة.

Checkpointنقطة فحص

1. Open the trace or run npx playwright test --ui. Which locator was it waiting for, and what did the page look like at that moment?1. افتح الـ trace أو شغّل npx playwright test --ui. كان مستني أنهي locator، والصفحة كان شكلها إيه في اللحظة دي؟

Checkpointنقطة فحص

2. Is every label, button text and heading in the test still exactly what the app shows?2. كل لابل وكلام زرار وعنوان في التست لسه هو بالظبط اللي التطبيق بيعرضه؟

Checkpointنقطة فحص

3. Does the page.route pattern match the URL you see in the network log, and does the fake JSON use the keys the app reads?3. الـ pattern بتاع page.route بيطابق الـ URL اللي شايفه في لوج الشبكة؟ والـ JSON المزيف بيستخدم المفاتيح اللي التطبيق بيقراها؟

Checkpointنقطة فحص

4. Do goto and toHaveURL still match the paths in app.routes.ts, and is the app running at baseURL?4. goto وtoHaveURL لسه مطابقين للمسارات اللي في app.routes.ts؟ والتطبيق شغّال على baseURL؟

Checkpointنقطة فحص

5. Did a page-object rename reach every spec? Playwright will not tell you before running; your editor or tsc will.5. تغيير اسم في الـ page object وصل لكل الـ specs؟ Playwright مش هيقولك قبل التشغيل؛ الإديتور أو tsc هما اللي هيقولوا.

Checkpointنقطة فحص

6. Is the file inside testDir and named *.spec.ts? A test that never runs never fails.6. الملف جوه testDir واسمه *.spec.ts؟ التست اللي عمره ما بيشتغل عمره ما بيفشل.

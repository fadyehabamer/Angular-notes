Signal-based state managementإدارة الحالة بالـ signals

A service with a private writable signal and public computed views is a complete state solution for most applications. This is what it looks like when you grow it — derived state, entity collections, optimistic updates and undo — before you ever consider a library.service فيها signal خاصة قابلة للكتابة وعروض computed عامة — دي حل حالة كامل لمعظم التطبيقات. وده شكلها لما تكبر — حالة مشتقة، ومجموعات entities، وتحديثات متفائلة، وتراجع — قبل ما تفكر في مكتبة أصلاً.

What it actually isهي إيه بالظبط

Signal-based state is keeping your app's data in signals inside a service, with methods as the only way to change it.الـ signal state معناها إنك تحط داتا التطبيق في signals جوه service، والميثودز هي الطريقة الوحيدة لتغييرها.

Think of it likeاعتبرها زي

A bank account. The balance is not a public variable anyone can edit — you deposit and withdraw through the counter.حساب بنكي. الرصيد مش متغيّر عام أي حد يعدّله — بتودّع وتسحب من الشباك.

You reach for it whenهتحتاجها لما

The moment a third component needs the same data, or a value must survive navigation.أول ما تالت component يحتاج نفس الداتا، أو قيمة لازم تعيش بعد التنقّل.

A plain signal store handles the overwhelming majority of applications. These are the specific signals that you have outgrown it — not a feeling that the app is "big", but concrete, nameable problems.الـ signal store العادي بيتعامل مع الغالبية العظمى من التطبيقات. ودي العلامات المحددة إنك كبرت عليه — مش إحساس إن التطبيق «كبير»، لكن مشاكل ملموسة وليها أسماء.

Watch outخد بالك

  • Keep the writable signal private and expose asReadonly(). Otherwise any component can .set() your state and you lose every guarantee.خلي الـ signal القابلة للكتابة private واعرض asReadonly(). غير كده أي component يقدر يعمل .set() لحالتك وبتضيّع كل الضمانات.
  • Never store what you can derive. Two fields that must agree will eventually disagree — the only fix is not to have two.عمرك ما تخزّن حاجة تقدر تشتقها. حقلين لازم يتفقوا هيختلفوا في الآخر — والحل الوحيد إنك متعملش اتنين.
  • Immutability is not optional. update(l => { l.push(x); return l; }) returns the same reference and nothing re-renders.عدم التغيير مش اختياري. update(l => { l.push(x); return l; }) بترجّع نفس الـ reference ومفيش حاجة بتترسم من الأول.
  • Do not put a signal inside another signal’s value. Nested signals make dependency tracking unpredictable — keep the state flat and derive shapes with computed.متحطش signal جوه قيمة signal تانية. الـ signals المتداخلة بتخلي تتبع الاعتماديات غير متوقع — خلي الحالة مسطحة واشتق الأشكال بـ computed.
  • A store per feature beats one giant AppStore. Global does not mean singular — CartStore, SessionStore, FiltersStore.store لكل فيتشر أحسن من AppStore واحد عملاق. «عام» مش معناها «واحد» — CartStore وSessionStore وFiltersStore.

Q01 Which belongs in a signal store, and which should be derived?أنهي حاجة مكانها الـ signal store، وأنهي واحدة تبقى مشتقّة؟
whyليه

Store the smallest set of facts you cannot work out, and derive everything else with computed(). Storing the visible list too means two things to keep in step, and one of them will drift.خزّن أصغر مجموعة حقائق مش بتقدر تحسبها، واشتق كل حاجة تانية بـ computed(). ولو خزّنت القائمة الظاهرة كمان يبقى عندك حاجتين لازم يفضلوا متوافقين، وواحدة فيهم هتنحرف.

Q02 How should a store expose its state to components?الـ store المفروض يعرض حالته للـ components إزاي؟
whyليه

Expose asReadonly() (or a computed()) and keep the WritableSignal private. Then every change goes through a named method — and when a value is wrong you know exactly which few lines could have done it.اعرض asReadonly() (أو computed()) وخلي الـ WritableSignal خاص. وساعتها كل تغيير بيمر من دالة لها اسم — ولما قيمة تطلع غلط تكون عارف بالظبط أنهي كام سطر ممكن يكونوا عملوها.

Q03 When is a signal store enough, without NgRx?إمتى الـ signal store يكفي، من غير NgRx؟
whyليه

A service holding signals plus computed() covers a lot of ground with no ceremony. Reach for NgRx when you actually want the things it sells: a serialisable action history, devtools, undo.service شايلة signals مع computed() بتغطي مساحة كبيرة من غير طقوس. واستخدم NgRx لما تكون عايز فعلاً اللي بيقدّمه: سجل أحداث قابل للتخزين، وdevtools، وتراجع.

Q04 update() versus set() for a nested object?update() مقابل set() لكائن متداخل؟
whyليه

The rule is about references, not which method you pick. update(s => ({ ...s, open: true })) is fine; update(s => { s.open = true; return s; }) returns the same object and changes nothing on screen.القاعدة عن المراجع، مش عن أنهي دالة تختار. update(s => ({ ...s, open: true })) تمام، أما update(s => { s.open = true; return s; }) فبترجّع نفس الكائن ومش بتغيّر حاجة على الشاشة.

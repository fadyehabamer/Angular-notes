Micro frontends and Module Federationالـ Micro frontends و Module Federation

Micro frontends let separate teams deploy parts of one application independently. This is an organisational solution to an organisational problem — and it is the most over-adopted pattern in frontend. Read the costs before the setup, because they are paid by everyone, forever.الـ micro frontends بتخلي فرق منفصلة تنشر أجزاء من تطبيق واحد بشكل مستقل. وده حل تنظيمي لمشكلة تنظيمية — وهو أكتر نمط بيتبنى في غير محله في الفرونت إند. اقرا التكاليف قبل الإعداد، لإن الكل بيدفعها، للأبد.

What it actually isهي إيه بالظبط

Micro frontends mean separate teams shipping separate apps that appear to the user as one page.الـ micro frontends معناها فرق منفصلة بتشحن تطبيقات منفصلة بتبان للمستخدم كأنها صفحة واحدة.

Think of it likeاعتبرها زي

A shopping mall. Every shop has its own staff, stock and opening hours, but the shopper walks through one building.مول تجاري. كل محل ليه موظفينه وبضاعته ومواعيده، بس الزبون بيتمشى في مبنى واحد.

You reach for it whenهتحتاجها لما

Several teams that genuinely cannot coordinate a release. It is an organisational fix, not a technical upgrade.لما كذا فريق مايقدروش فعلاً ينسّقوا إصدار واحد. ده حل تنظيمي، مش ترقية تقنية.

The whole idea in 4 picturesالفكرة كلها في 4 صور

Independent buildsبناء مستقل

Each app has its own repo, pipeline and release date. That is the whole point.كل تطبيق ليه repo وpipeline وتاريخ إصدار. ودي الفكرة كلها.

A shell hosts themالقشرة بتستضيفهم

One host app owns routing, layout and whatever the user thinks of as the site.تطبيق مضيف واحد بيملك التوجيه والتخطيط واللي المستخدم شايفه كموقع.

Modules load remotelyالموديولات بتتحمّل عن بُعد

Module Federation fetches code from another origin at runtime, not at build time.Module Federation بيجيب كود من مصدر تاني وقت التشغيل، مش وقت البناء.

Shared deps are the painالمكتبات المشتركة هي الوجع

Two Angular versions in one page is where the days disappear. Pin them, hard.نسختين أنجولار في صفحة واحدة هي اللي بتضيّع الأيام. ثبّتهم بحزم.

Real exampleمثال حقيقي What most teams actually neededاللي معظم الفرق كانت محتاجاه فعلاً

The stated problem is usually "four teams keep blocking each other". The cause is almost never the deployment unit — it is that everything imports everything. Enforced module boundaries fix that without a single runtime dependency.المشكلة المعلنة عادةً «أربع فرق بيعطّلوا بعض». والسبب تقريباً عمره ما بيكون وحدة النشر — السبب إن كل حاجة بتعمل import لكل حاجة. والحدود المفروضة بتحل ده من غير ولا اعتمادية وقت تشغيل.

enforced boundaries, one deploymentlint ruleقاعدة lint
// eslint: @nx/enforce-module-boundaries (or a plain import rule){  "depConstraints": [    { "sourceTag": "scope:checkout",      "onlyDependOnLibsWithTags": ["scope:checkout", "scope:shared"] },     { "sourceTag": "scope:catalogue",      "onlyDependOnLibsWithTags": ["scope:catalogue", "scope:shared"] },     { "sourceTag": "scope:shared",      "onlyDependOnLibsWithTags": ["scope:shared"] }  ]} // now team A CANNOT import team B's internals — the build fails.// teams are isolated, ownership is clear, and there is still// one deployment, one Angular, one CI and one bundle to debug.

Watch outخد بالك

  • Angular must be a singleton. Two copies in one page means two injector trees and bugs that make no sense — this is the number one federation failure.أنجولار لازم يكون singleton. ونسختين في صفحة واحدة معناها شجرتين injector وباجات مالهاش أي معنى — وده الفشل رقم واحد في الـ federation.
  • Version skew is a runtime failure in production. Team A upgrades Angular, team B has not, and the page breaks for users — not in anybody’s CI.اختلاف الإصدارات ده فشل وقت التشغيل في الإنتاج. فريق A بيرقّي أنجولار وفريق B لأ، والصفحة بتتكسر عند المستخدمين — مش في CI حد.
  • A remote is a network dependency you do not control. Decide now what the user sees when it is down, and build that screen.الـ remote اعتمادية شبكة إنت مش متحكم فيها. قرر دلوقتي المستخدم هيشوف إيه لما تقع، وابني الشاشة دي.
  • Shared state across remotes is the hardest part. Auth, theme and routing need an explicit contract — usually an injection token exposed by the shell.الحالة المشتركة بين الـ remotes أصعب جزء. الـ auth والثيم والـ routing محتاجين عقد صريح — وغالباً injection token بيعرضه الـ shell.
  • If you cannot explain in one sentence why lazy routes and a monorepo fail for you, you do not need this. That is not a slogan — it is the most common expensive mistake in frontend architecture.لو مش قادر تشرح في جملة واحدة ليه الراوتس الكسلانة والـ monorepo مش نافعين معاك، يبقى إنت مش محتاج ده. ودي مش شعار — دي أشهر غلطة غالية في معمار الفرونت إند.
If you remember one thingلو هتفتكر حاجة واحدة

This is the most expensive architecture in the list. If one team can ship the whole app, do not do this.دي أغلى معمارية في اللستة كلها. لو فريق واحد يقدر يشحن التطبيق كله، ماتعملهاش.

Q01 What problem do micro-frontends actually solve?الـ micro-frontends بتحل مشكلة إيه فعلاً؟
whyليه

The win is organisational: the checkout team ships without waiting for anyone. Technically you pay for it — duplicate framework code, harder debugging, shared-version headaches.المكسب تنظيمي: فريق الدفع بينشر من غير ما يستنى حد. وتقنياً إنت بتدفع التمن — كود framework مكرر، وتتبع أخطاء أصعب، وصداع إصدارات مشتركة.

Q02 When should you not use them?إمتى ماينفعش تستخدمهم؟
whyليه

With one team, lazy-loaded routes give you the same code splitting with none of the coordination cost. Micro-frontends are an answer to an organisational problem, so reach for them when you have that problem.مع فريق واحد، المسارات المؤجّلة بتدّيك نفس تقسيم الكود من غير أي تكلفة تنسيق. والـ micro-frontends إجابة لمشكلة تنظيمية، فاستخدمهم لما تكون المشكلة دي عندك.

Q03 What is the main technical risk?إيه الخطر التقني الأساسي؟
whyليه

Shared singletons and framework internals assume one version. Drift produces baffling runtime errors, which is why teams end up enforcing a shared version policy — and why the independence is never total.الـ singletons المشتركة وتفاصيل الـ framework بتفترض إصدار واحد. والانحراف بيطلّع أخطاء وقت تشغيل محيّرة، وعلشان كده الفرق بتنتهي بفرض سياسة إصدار مشترك — وعلشان كده الاستقلال مبيبقى كامل أبداً.

Q04 How should two micro-frontends share state?إزاي اتنين micro-frontends يشاركوا الحالة؟
whyليه

Every shared thing is coupling, and coupling is what you were trying to escape. Keep the surface tiny and explicit, so a remote can change internally without breaking the shell.كل حاجة مشتركة هي ارتباط، والارتباط هو اللي كنت بتهرب منه. خلي السطح صغير وصريح، علشان أي remote يقدر يتغيّر من جوه من غير ما يكسر الـ shell.

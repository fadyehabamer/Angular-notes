End-to-end testing with Playwrightاختبار شامل بـ Playwright

A unit test proves a component works. An end-to-end test proves the app works — a real browser, your real build, a real server, clicking real buttons. You want very few of these, and they should cover the journeys that would cost you money if they broke.تست الوحدة بيثبت إن الـ component شغال. والتست الـشامل بيثبت إن التطبيق شغال — براوزر حقيقي، وbuild حقيقي، وسيرفر حقيقي، وكليك على زراير حقيقية. وإنت عايز قليل جداً منهم، ولازم يغطوا الرحلات اللي لو وقعت هتكلفك فلوس.

What it actually isهي إيه بالظبط

End-to-end testing means a robot really opens your app in a real browser and clicks through it like a person.اختبار الطرف للطرف معناه إن روبوت بيفتح تطبيقك فعلاً في متصفح حقيقي وبيدوس فيه زي أي إنسان.

Think of it likeاعتبرها زي

A mystery shopper. Not inspecting the shelves — actually walking in, buying something, and reporting whether it worked.مشتري سرّي. مش بيفتّش على الرفوف — بيدخل فعلاً، ويشتري حاجة، ويقول اشتغلت ولا لأ.

You reach for it whenهتحتاجها لما

For the two or three journeys that must never break: sign in, check out, submit the thing you get paid for.للاتنين تلاتة رحلات اللي ماينفعش يقعوا: تسجيل الدخول، والدفع، وإرسال الحاجة اللي بتتدفعلك عليها.

Start the real appشغّل التطبيق الحقيقي

Drive it like a userسوقه زي المستخدم

Find elements by visible text or role — never by a CSS class that will be renamed.دوّر على العناصر بالنص الظاهر أو الدور — مش بـ class هيتغيّر اسمه.

Wait for state, not timeاستنى الحالة مش الوقت

Auto-waiting for a condition. A hard-coded sleep is how flakiness is born.استنى شرط يتحقق. الـ sleep الثابت هو أصل التقلّب.

Every name on this page — yours or Angular’s?كل اسم في الصفحة دي — بتاعك ولا بتاع أنجولار؟

An E2E test knows nothing about your code. The orange names here are what the user sees: button labels, form labels, a data-testid. Rename the text on a button in the app and the test breaks, even though no TypeScript changed. The role words (button, link, heading) are fixed by the browser.تيست الـ E2E مايعرفش أي حاجة عن الكود بتاعك. الأسماء البرتقاني هنا هي اللي اليوزر بيشوفه: كلام الزراير، اللابلز بتاعة الفورم، وdata-testid. لو غيّرت الكلام اللي على زرار في التطبيق التيست هيقع، مع إن ولا سطر TypeScript اتغير. وكلمات الـ role (button وlink وheading) ثابتة من المتصفح.

Watch outخد بالك

  • Never use a fixed waitForTimeout. Assert on the state you are waiting for and let the runner retry — this is the single biggest cause of flaky suites.عمرك ما تستخدم waitForTimeout ثابت. أكّد على الحالة اللي بتستناها وسيب الـ runner يعيد — ده أكبر سبب للتستات المتقلبة.
  • Select by role and visible text, not by CSS class. Class names change with every refactor; a button’s accessible name does not.اختار بالدور والنص الظاهر، مش بـ CSS class. أسماء الـ classes بتتغير مع كل إعادة هيكلة؛ أما الاسم المتاح للزرار فلأ.
  • Control the network with page.route() for anything you do not own. A test that depends on a third-party sandbox fails on their schedule, not yours.تحكّم في الشبكة بـ page.route() لأي حاجة مش بتاعتك. التست اللي بيعتمد على sandbox خارجية بتفشل حسب جدولهم، مش جدولك.
  • Each test must set up and clean up its own data. Tests that depend on the order they run in fail the moment someone enables parallelism.كل تست لازم يجهّز وينضّف الداتا بتاعته. والتستات اللي بتعتمد على ترتيب التشغيل بتفشل أول ما حد يشغّل التوازي.
  • E2E tests are slow and expensive by nature. If your suite exceeds five minutes, move assertions down to component tests instead of adding machines.التستات الشاملة بطيئة وغالية بطبيعتها. ولو مجموعتك عدّت خمس دقايق، انقل التأكيدات لتستات الـ components بدل ما تزوّد أجهزة.
If you remember one thingلو هتفتكر حاجة واحدة

Write few of these and keep them stable. A flaky suite everyone ignores is worse than no suite at all.اكتب قليل منهم وخليهم ثابتين. مجموعة اختبارات متقلّبة الكل بيتجاهلها أوحش من مفيش اختبارات أصلاً.

Q01 What does an end-to-end test exercise that a unit test does not?اختبار الطرف للطرف بيجرّب إيه واختبار الوحدة لأ؟
whyليه

It is the only level that proves the pieces fit. It is also the slowest and most brittle, which is why you want a few e2e journeys over the critical flows and many fast unit tests underneath.ده المستوى الوحيد اللي بيثبت إن القطع بتتلاقي مع بعض. وهو كمان الأبطأ والأكثر هشاشة، وعلشان كده إنت عايز كام رحلة e2e على المسارات الحرجة وتحتها اختبارات وحدة كتير وسريعة.

Q02 What is a page object for?الـ page object بيستخدم لإيه؟
whyليه

When a button's markup changes you fix one file, not twenty tests. It also makes the specs read like the user story rather than a pile of CSS selectors.لما ماركب زرار يتغيّر بتصلّح ملف واحد، مش عشرين اختبار. وكمان بيخلي الاختبارات تتقرا زي قصة المستخدم مش كومة CSS selectors.

Q03 Which selector is most robust in an e2e test?أنهي selector أمتن في اختبار e2e؟
whyليه

Roles and test ids survive restyling, and roles double as an accessibility check. Generated classes and positions change the moment a designer touches the page.الـ roles وتعريفات الاختبار بتنجو من إعادة التنسيق، والـ roles كمان بتعمل فحص إتاحة في نفس الوقت. أما الكلاسات المتولّدة والمواضع فبتتغير أول ما مصمّم يلمس الصفحة.

Q04 How should an e2e suite handle the backend?مجموعة اختبارات e2e المفروض تتعامل مع الـ backend إزاي؟
whyليه

Tests that depend on whatever data exists fail randomly, and a flaky suite gets ignored. Seed the state you need, or intercept the calls and reply with fixtures.الاختبارات اللي بتعتمد على أي بيانات موجودة بتفشل عشوائياً، والمجموعة المتقلّبة بيتم تجاهلها. جهّز الحالة اللي محتاجها، أو اعترض الطلبات ورُد ببيانات ثابتة.

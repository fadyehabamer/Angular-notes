SSR and hydration: the same DOM, twiceSSR والـ hydration: نفس الـ DOM، مرتين

The server renders your components to HTML and sends it. The browser paints it immediately, then Angular boots and adopts that existing DOM instead of throwing it away. Every bug in this area comes from the two renders disagreeing.السيرفر بيرندر الـ components بتاعتك HTML ويبعتها. البراوزر بيرسمها على طول، وبعدين أنجولار بيقلع ويتبنّى الـ DOM الموجود بدل ما يرميه. وكل باج في المنطقة دي سببه إن الرندرتين مش متفقين.

What it actually isهي إيه بالظبط

SSR means the server sends real HTML, so the user sees content before any JavaScript has run.الـ SSR معناه إن السيرفر بيبعت HTML حقيقي، فالمستخدم بيشوف محتوى قبل ما أي JavaScript تشتغل.

Think of it likeاعتبرها زي

Getting a printed menu at the door instead of waiting for a waiter to describe the whole thing out loud.تاخد منيو مطبوع عند الباب بدل ما تستنى الجرسون يقرالك المنيو كله بصوت عالي.

You reach for it whenهتحتاجها لما

Public pages that need to appear fast or be found by search engines. Not internal dashboards behind a login.الصفحات العامة اللي لازم تظهر بسرعة أو محركات البحث تلاقيها. مش داشبورد داخلي ورا تسجيل دخول.

The server rendersالسيرفر بيرسم

Angular runs without a browser and produces finished HTML for that URL.أنجولار بيشتغل من غير متصفح وبيطلّع HTML جاهز للـ URL ده.

The user sees it fastالمستخدم بيشوفها بسرعة

Readable content immediately. It is not interactive yet, but it is there.محتوى مقروء على طول. لسه مش تفاعلي، بس موجود.

Hydration wakes it upالـ hydration بيصحّيها

Angular adopts the existing DOM and attaches listeners instead of rebuilding.أنجولار بيتبنّى الـ DOM الموجود وبيلزق الـ listeners بدل ما يعيد البناء.

Browser-only code breaks itكود المتصفح بيكسّرها

window, localStorage, random values. Guard them or defer them.window وlocalStorage والقيم العشوائية. احميهم أو أجّلهم.

The article body is text — it never needs to become interactive. The comment form does, but only if somebody scrolls down and clicks it. Incremental hydration lets one page be static and interactive at the same time, per region.جسم المقال نص — عمره ما هيحتاج يبقى تفاعلي. فورم التعليقات محتاج، بس لو حد نزل ودوس عليه. الـ incremental hydration بيخلي الصفحة الواحدة ثابتة وتفاعلية في نفس الوقت، كل منطقة على حدة.

Watch outخد بالك

  • window, document and localStorage do not exist on the server. Guard with isPlatformBrowser, or better, use afterNextRender(), which only ever runs in the browser.window وdocument وlocalStorage مش موجودين على السيرفر. احمي نفسك بـ isPlatformBrowser، أو الأحسن استعمل afterNextRender() اللي عمره ما بيشتغل غير في البراوزر.
  • NG0500 / hydration mismatch means the two renders produced different DOM. Usual causes: random values, dates, direct DOM manipulation, or invalid HTML nesting the browser silently corrects.NG0500 / hydration mismatch معناها إن الرندرتين طلعوا DOM مختلف. الأسباب المعتادة: قيم عشوائية، أو تواريخ، أو تعديل مباشر على الـ DOM، أو تداخل HTML غلط البراوزر بيصلحه في صمت.
  • Invalid nesting is a sneaky one: a <div> inside a <p> is re-parented by the browser, so the client DOM no longer matches what the server sent.التداخل الغلط ده خبيث: <div> جوه <p> البراوزر بينقله، فالـ DOM عند الكلاينت مبقاش مطابق للي السيرفر بعته.
  • provideHttpClient(withFetch()) is not optional under SSR — without it the transfer-state cache does not kick in and every request runs twice.provideHttpClient(withFetch()) مش اختيارية مع الـ SSR — من غيرها الـ transfer-state cache مبيشتغلش وكل ريكويست بيتعمل مرتين.
  • You can opt a subtree out entirely with ngSkipHydration on the element. It is an escape hatch for a stubborn third-party widget, not a fix.تقدر تستثني فرع كامل بـ ngSkipHydration على العنصر. ده مخرج طوارئ لويدجت خارجية عنيدة، مش حل.
If you remember one thingلو هتفتكر حاجة واحدة

Hydration reuses the server's DOM instead of throwing it away. Touching window during render is what breaks it.الـ hydration بيعيد استخدام الـ DOM بتاع السيرفر بدل ما يرميه. ولمس window أثناء الرسم هو اللي بيكسّره.
